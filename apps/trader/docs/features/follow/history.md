# F8 follow — 기록

> [트레이더 허브](../../README.md) · [계획](plan.md) · [스키마 §15](../../schema.md) · [테스트](testing.md)

설계 판단 · 버그 · 검증 결과를 남긴다. 진행 상태는 [진행 현황](../../status.md)에만 적는다.

## 2026-08-30 — 구현

### 차단이 팔로우 엣지를 지우기로 했다

[차단 계획](../safety/plan-block.md)이 "F8 착수 시점까지 미룬다"고 명시해 둔
결정이다. 지우는 쪽을 골랐고, `blocks` 에 `after insert` 트리거를 달았다.

지우지 않는 선택지도 실제로 동작한다 — 목록 뷰의 `is_blocked_with()` 필터가
이미 화면에서 가려 주기 때문이다. 그런데 그러면 **수와 목록이 어긋난다.**
차단한 상대가 팔로워 수에는 계속 잡히고, 그 수를 눌러 들어간 목록에서만
사라진다. 수를 조회자별로 필터링해 맞추는 방법도 있지만 그러면 같은 프로필의
팔로워 수가 사람마다 달라진다 — 더 나쁜 어긋남이다.

대가는 차단 계획이 근거로 삼았던 "차단에는 자식이 달리지 않는다"가 더 이상
참이 아니게 된 것이다. 마이그레이션 주석과 [스키마 §15](../../schema.md)에
그 사실을 적었다. 차단을 해제해도 팔로우는 되살아나지 않는다.

트리거가 있어도 목록 뷰의 필터는 함께 남긴다. 트리거는 **나와 상대 사이의**
엣지만 지우고, 제3자의 팔로워 목록에서 차단 상대를 만나는 경우는 덮지 못한다.

### 조회를 전체 공개로 열었다

`blocks` 는 본인 행만 보이는데 `follows` 는 `using (true)` 다. 남의 프로필에서도
팔로워 수와 목록이 보여야 하기 때문이다. 본인 행만 열면 수 · 목록 · 맞팔 판정이
전부 `security definer` 함수를 타야 하고, 그 함수가 결국 같은 것을 공개하게 된다.
팔로우 그래프가 공개라는 것을 결정으로 적어 두는 편이 낫다.

### 팔로잉 피드는 뷰를 하나 더 두는 쪽으로

PostgREST 로 "내가 팔로우한 사람의 글"을 거르려면 계산 컬럼이나 필터 흉내가
필요하다. `posts_with_author` 를 `follows` 로 좁힌 뷰를 하나 두면 커서 · 컬럼 ·
정렬이 그대로라 **앱은 읽는 대상만 바꾼다**(`FeedSource`). 감싸는 뷰라 삭제 ·
차단 필터도 다시 쓰지 않는다.

탭 둘이 `FeedCubit` 하나를 공유한다. 탭마다 cubit 을 두면 작성 · 수정 · 삭제 ·
차단의 결과를 어느 목록에 반영할지 화면이 매번 정해야 한다. 대가는 탭을 옮길 때
다시 읽는 것(스크롤 위치 초기화)이고, 화면 주석에 적었다.

### 관계는 프로필 조회에 얹었다

`FollowActionCubit` 은 관계를 스스로 묻지 않고 화면이 `seed()` 로 심어 준다.
`profile_details` 가 프로필과 함께 내려주기 때문이다. `BlockActionCubit` 이
상태를 따로 조회하는 것과 갈리는데, 이유는 차단이 프로필 응답에 들어 있지
않아서다 — 차단 사실을 공개 뷰에 실을 수 없다.

낙관적 업데이트는 관계와 팔로워 수를 **한 상태에 함께** 담는다. 버튼만 바뀌고
수가 그대로면 실패한 것처럼 보이고, 되돌릴 값이 두 곳에 흩어지면 복원이
어긋난다.

### 차단 거부 문구는 방향 중립이다

`follows_insert_own` 의 차단 검사는 `is_blocked_with()` 라 양방향이다. 거부를
보는 쪽이 차단을 건 쪽이라고 가정할 수 없으므로 "지금은 팔로우할 수 없습니다"
하나로 끝낸다. 차단 계획의 [일반화된 규칙](../safety/plan-block.md)을 그대로
따랐다. 프로필 화면은 내가 차단한 상대에게는 아예 버튼을 그리지 않는다.

### 42501 을 데이터 원본에서만 코드로 바꾼다

공용 `SupabaseErrorMapper` 는 `42501` 을 일반 권한 오류로 옮긴다. 팔로우 삽입에서
오는 `42501` 은 사실상 차단 검사 하나뿐이라(`follower_id` 는 애초에 보내지 않는다)
`SupabaseFollowDataSource.followUser` 에서만 `FailureCode.followBlocked` 를 붙였다.
공용 mapper 에 넣으면 모든 RLS 거부가 팔로우 문구로 바뀐다.

### 검증

- `supabase/tests/follow_rls_check.py` 28건 통과 (실제 JWT + REST).
  차단 상호작용 · 조회자별 목록 차이 · 탈퇴 cascade 를 포함한다
- `flutter analyze` 무결함, `flutter test` 전체 통과

## 2026-08-30 — 검수와 수정

서브에이전트 넷으로 다국어와 F8 을 훑고 나온 것을 고쳤다. 앱 계층 P1 둘과
데이터 계층 P2 둘이 실질 결함이었다.

### 응답이 요청보다 늦게 오는 자리를 전부 놓치고 있었다

`FeedCubit` 과 `FollowListCubit` 둘 다 요청을 보낼 때 소스·커서를 읽고,
응답을 `emit` 할 때는 그 응답이 지금 것인지 확인하지 않았다. 가드가
`isClosed` 하나뿐이었다.

깨지는 순서가 둘이다. (a) 전체 탭 조회가 날아가 있는 동안 팔로잉 탭으로
옮기면, 늦게 온 전체 응답이 팔로잉 탭에 눌러앉는다. (b) `loadMore` 중에
탭을 옮기면 늦게 온 **다음 페이지**가 팔로잉 목록 뒤에 붙고 `nextCursor` 까지
전체 피드 것으로 덮여, 그 뒤 무한스크롤이 통째로 전체 피드가 된다.

`_generation` 토큰을 둬서 `_load` 가 값을 올리고, 요청 쪽이 보내기 전에
잡아 두었다가 응답 시점에 달라졌으면 버린다. `FollowListCubit` 의 새로고침 ×
더 읽기 경합도 같은 장치로 닫았다 — 그쪽 주석은 "최신 state 위에 병합한다"고
적었지만, 그 경우 옛 페이지는 **버려야** 하는 것이었다.

커밋 메시지에 "탭 둘이 cubit 하나를 공유하는 대가는 재조회"라고 적었는데,
실제 대가는 재조회가 아니라 **소스 간 응답 교차**였다.

### 팔로우 버튼이 화면 수명 동안 한 번만 심어졌다

`seed` 를 부르는 listener 가 `previous.profile?.id != current.profile?.id` 로
걸려 있었다. 같은 사람을 다시 읽는 당겨서 새로고침에서는 거짓이라, 팔로잉
수는 갱신되는데 팔로워 수와 버튼만 옛 값에 멈췄다. 그 상태로 누르면 이미 있는
행을 다시 넣으려다 실패한다. listener 를 둘로 나눠 하나는 id 변경(글 목록 ·
차단 상태), 하나는 프로필 값 변경(팔로우 버튼)에 걸었다.

### 해제는 멱등이어야 한다

`unfollowUser` 가 `.select().single()` 을 붙여 0행 삭제를 `PGRST116` 으로
올리고 있었다. 그런데 `follows` 행은 내가 지우지 않아도 사라진다 —
`blocks_drop_follows` 가 상대의 차단만으로도 지운다. 그 경우 화면은 '팔로잉'
인데 행은 없고, 눌러도 실패한 뒤 **다시 '팔로잉'으로 되돌아간다.**
`unblockUser` 는 `.single()` 이 맞다(`blocks` 행은 내가 지우지 않는 한
사라지지 않는다) — 비대칭의 이유를 데이터 원본 주석에 적었다.

### 팔로우 삽입과 차단이 겹치면 엣지가 살아남았다

정책의 `is_blocked_with()` 검사도, `blocks` 의 트리거도 "상대가 이미
커밋했다"를 전제한다. READ COMMITTED 에서 겹치면 둘 다 성공한다. 남은 엣지는
차단당한 쪽 화면에 "팔로잉 중"으로 뜨고, 차단한 쪽에서는 수(1)와 목록(0행)이
어긋난다 — 트리거를 도입한 근거였던 그 어긋남이다. 재차단으로도 복구되지
않는다(`blocks` PK 충돌로 after insert 가 발화하지 않는다).

`follow_pair_lock()` advisory 락을 양쪽 경로가 잡게 하고, `follows` 에
BEFORE INSERT 가드를 더했다 (`20260830150000_harden_follows.sql`).
`supabase/tests/follow_block_race_check.py` 가 psql 세션 둘로 재현하고,
락을 빼면 4건이 모두 실패하는 것으로 검사가 공허하지 않음을 확인했다.

### 고치지 않고 기록만 한 것

- 팔로잉 피드가 페이지마다 팔로이 전체 글을 펼친다(19배). RPC 로 조회 경로를
  바꿔야 해서 앱 커서 계약까지 번진다 — [스키마 §15](../../schema.md)
- 목록 뷰의 차단 필터는 화면 필터이지 보안 통제가 아니다 (`follows` 직접
  조회로 우회된다). "팔로우 그래프는 공개다"가 확정 결정이라 그대로 둔다
- 엣지 삭제로 차단당한 쪽이 차단 사실을 추론할 수 있다. F7 의 "알리지 않는다"
  에서 의도적으로 이탈한 것이라 [계획](plan.md)의 결정 표에 적었다

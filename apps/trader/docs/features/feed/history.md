## 1. post 와 feed 를 나눈 이유

같은 `posts` 테이블을 쓰지만 앱에서는 분리했다. 나누는 기준을 **테이블**이 아니라
**변경 이유**로 잡았다.

- `post` — 게시물 한 건의 작성 · 수정 · 삭제. 바뀌는 이유는 "게시물에 필드가 늘 때"다
- `feed` — 목록 조회. 바뀌는 이유는 "목록에 무엇을 더 얹느냐"다. 반응 수 · 댓글 수 ·
  차단 필터 · 팔로잉 필터가 모두 여기로만 들어온다

경계는 domain entity 에서 만난다. 피드는 게시물을 자기 타입으로 다시 만들지 않고
post 의 `Post` 를 그대로 쓴다 (아키텍처 규칙 ⑥ — feature 간 참조는 domain 까지).

## 2. 커서 페이지네이션 — `OFFSET` 을 쓰지 않는다

`OFFSET` 은 스크롤 중에 새 글이 올라오면 그만큼 밀린다. 2페이지를 요청하는 사이에
글이 하나 올라오면 1페이지의 마지막 글이 2페이지에 다시 나온다. 삭제되면 반대로
한 건이 건너뛰어진다.

`(created_at, id)` 복합 커서를 쓴다.

```text
created_at < c.created_at
  or (created_at = c.created_at and id < c.id)
```

`id` tie-break 가 없으면 `created_at` 이 같은 게시물이 여러 개일 때 경계에서 중복이
생긴다. 밀리초 단위라 실제로 잘 겹치지 않지만, "겹치지 않을 것"에 정확성을 맡기는
설계는 두지 않았다.

### 커서는 불투명 문자열이다

`FeedCursor` 는 `base64url("<iso8601>|<uuid>")` 로 인코딩하고, **data 계층 밖으로는
문자열만 나간다.** domain 과 presentation 은 해석하지 않고 그대로 되돌려준다.
나중에 커서 표현을 바꿔도 바깥 계층이 영향을 받지 않는다.

### 다음 페이지 유무는 `limit + 1` 로 안다

전체 개수를 세는 `COUNT` 를 매번 돌리지 않는다. `limit + 1` 개를 요청해서 초과분이
오면 다음 페이지가 있는 것이고, 초과분은 잘라 버린다.

**다음 커서는 잘라낸 항목이 아니라 마지막으로 돌려준 항목으로 만든다.** 반대로 하면
다음 페이지에서 한 건이 건너뛰어진다. 테스트로 고정해 뒀다.

## 3. 작성자 프로필 조인 (2026-08-22)

### 문제

카드에 작성자를 보여줘야 하는데 `posts` 에는 `author_id` 밖에 없다. 처음에는 그
UUID 의 첫 글자를 아바타에 넣어 두고 넘어갔다.

목록을 받은 뒤 작성자를 한 명씩 조회하는 방법은 처음부터 제외했다. 20개짜리
페이지마다 최대 20번의 왕복이 더 생긴다(N+1). [기획 F4](../../overview.md)도 반응 수 ·
댓글 수를 두고 같은 이유로 "뷰 또는 RPC 함수로 한 번에 내려준다"고 정해 뒀다.

### 선택지

| 방식 | 오늘의 비용 | 나중의 비용 |
|---|---|---|
| PostgREST 임베디드 조인 (`select('..., profiles(...)')`) | 마이그레이션 0개 | 차단 필터·집계가 붙을 때마다 select 문자열이 화면마다 늘어난다 |
| **DB 뷰** | 마이그레이션 1개 | 뷰 하나만 고치면 읽는 쪽은 그대로다 |
| RPC 함수 | 마이그레이션 1개 + 커서 코드 재작성 | 페이지 크기·정렬이 바뀔 때마다 시그니처 마이그레이션 |

**뷰를 골랐다.** RPC 는 커서 조건을 SQL 안에서 검증할 수 있다는 장점이 있지만,
불투명 커서를 `created_at` · `id` 두 파라미터로 풀어 넘겨야 해서 잘 동작하는 커서
설계와 그 테스트를 상당 부분 다시 써야 했다. 얻는 것에 비해 비쌌다.

### 구현

[`20260822140000_add_posts_with_author_view.sql`](../../../../../supabase/migrations/20260822140000_add_posts_with_author_view.sql)
가 `posts_with_author` 뷰를 만든다. 앱에서 바뀐 것은 조회 대상 이름과 컬럼 목록뿐이고,
커서 조립 · 정렬 · `limit` 코드는 그대로다. 현재 모습은 [스키마 §6](../../schema.md)에 있다.

### 함정 — `security_invoker = on`

**이게 이 작업에서 가장 위험했던 한 줄이다.**

Postgres 뷰는 기본적으로 **뷰 소유자**(`postgres`) 권한으로 실행된다. 그대로 두면
`posts_select_visible`(`deleted_at is null`)이 평가되지 않아 **삭제된 게시물이 피드에
그대로 나온다.** `profiles` 의 RLS 도 함께 무력화된다.

[스키마 §2](../../schema.md)가 "앱 쿼리마다 필터를 붙이는 방식은 화면이 늘면 언젠가
빠뜨린다"며 삭제행 숨김을 DB 에 맡겨 뒀는데, 뷰 하나가 그 보장을 통째로 우회하는
구조다. `with (security_invoker = on)` 을 붙이면 뷰를 **조회한 세션 사용자**의 권한으로
기반 테이블 정책이 그대로 평가된다.

앞으로 이 프로젝트에 추가되는 모든 뷰에 같은 규칙이 적용된다.

### 인덱스

뷰는 저장된 질의라 별도 인덱스가 없다. 기존
`posts_created_at_idx (created_at desc, id desc) where deleted_at is null` 를 그대로 탄다.
플래너가 `posts` 를 인덱스 순으로 훑다가 `LIMIT` 만큼만 `profiles` 를 PK 로 붙이므로
비용은 조인 전과 같다.

### 앱 쪽 타입 — `Post` 에 닉네임을 넣지 않았다

`FeedPost = Post + PostAuthor` 로 감쌌다. `Post` 에 필드를 더하면 작성자 프로필이
필요 없는 게시물 작성·수정 화면까지 그 값을 채워야 한다.

덕분에 **수정 결과를 반영할 때 작성자를 그대로 둘 수 있다**(`FeedPost.withPost`).
수정 화면은 `Post` 만 돌려주는데, 거기서 작성자를 다시 만들게 했다면 그 화면이
프로필까지 알아야 하고 값이 비는 순간 목록에서 이름이 사라진다.

`PostAuthor` 는 post feature 가 소유한다. 작성자는 게시물의 성질이고, 이 타입을 쓰는
`PostTile` 도 post 에 있다. profile 의 `Profile` 을 재사용하지 않은 이유는 `bio` ·
`createdAt` · `updatedAt` 까지 요구하기 때문이다 — 목록이 내려주지 않는 값을 채우려면
결국 프로필을 다시 조회해야 하고, 그게 없애려던 N+1 이다.

`PostTile` 의 `author` 는 필수 인자다. 값이 없을 때 보여줄 그럴듯한 대체 표시를
만들어 두면 조인을 빠뜨린 화면이 조용히 넘어간다.

### 새 글을 목록에 넣을 때

작성 성공 결과에는 작성자가 없다. 작성자는 **로그인한 본인**이므로 화면이 세션
(`AuthBloc` 의 `AppUser`)에서 만들어 붙인다. 이것 하나 때문에 방금 쓴 글을 서버에서
다시 조회하지 않는다.

## 4. 함께 고친 것 — 제약 이름이 어긋나 있었다

`20260822120000` 마이그레이션이 `feed_posts` → `posts` 로 rename 하면서 제약 이름도
`posts_content_length` 로 바꿨는데, `SupabaseErrorMapper` 는 옛 이름
`feed_posts_content_length` 를 그대로 보고 있었다. 500자를 넘겨 저장하면 사용자 문구
대신 DB 원문이 그대로 올라간다.

[스키마 §7](../../schema.md)의 "rename 은 딸린 객체 이름을 바꾸지 않는다"가 **앱 코드
쪽에도 남은 흔적**이었다. 매퍼를 고치고 회귀 테스트를 붙였다.

## 2026-08-24 — 화면 개편

하단 내비게이션이 생기면서 피드는 셸의 탭 본문이 됐다. 그에 맞춰 화면 밖으로 나가는
동작(로그아웃)을 AppBar 에서 뺐고, 새로고침도 당겨서 새로고침 하나로 모았다 — 같은
일을 하는 입구가 둘이면 AppBar 만 붐빈다.

- `FeedPlaceholder` — 비어 있음과 실패가 "아이콘 + 한 줄 + 행동 하나"로 모양이 같아
  한 위젯으로 묶었다. 스크롤은 스스로 만들지 않는다. 당겨서 새로고침이 빈 화면에서도
  동작해야 하므로 스크롤 뷰는 목록 쪽이 감싼다
  → **2026-08-27: `design_system/widget/app_placeholder.dart` 로 승격했다.** 같은
  모양이 프로필 · 댓글 · 차단 목록까지 넷이 되어 승격 기준을 넘겼다. 아이콘은
  선택 인자가 됐고 나머지 셋은 지웠다
- `FeedListFooter` — "더 읽는 중"과 "여기가 끝"은 전혀 다른 소식인데, 전에는 둘 다
  아무것도 아닌 화면으로 보였다. 마지막 한 칸을 꼬리표 자리로 고정했다
- 빈 목록에서 바로 작성으로 들어갈 수 있게 했다

`FeedCubit` 에는 `applyCommentCount` 가 더해졌다(F6). 댓글 화면에서 돌아올 때 목록을
다시 읽지 않고 그 항목의 수만 고친다.

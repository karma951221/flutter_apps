## 2026-08-30 — 구현

### 차단이 팔로우 엣지를 지우기로 했다

[차단 계획](../safety/plan-block.md)이 "F8 착수 시점까지 미룬다"고 명시해 둔
결정이다. 지우는 쪽을 골랐고, `blocks` 에 `after insert` 트리거를 달았다.

지우지 않는 선택지도 실제로 동작한다 — 목록 뷰의 `is_blocked_with()` 필터가
이미 화면에서 가려 주기 때문이다. 그런데 그러면 **수와 목록이 어긋난다.**
차단한 상대가 팔로워 수에는 계속 잡히고, 그 수를 눌러 들어간 목록에서만
사라진다. 수를 조회자별로 필터링해 맞추는 방법도 있지만 그러면 같은 프로필의
팔로워 수가 사람마다 달라진다 — 더 나쁜 어긋남이다.

대가는 차단 계획이 근거로 삼았던 "차단에는 자식이 달리지 않는다"가 더 이상
참이 아니게 된 것이다. 마이그레이션 주석과 [스키마 §15](../../schema.md)에
그 사실을 적었다. 차단을 해제해도 팔로우는 되살아나지 않는다.

트리거가 있어도 목록 뷰의 필터는 함께 남긴다. 트리거는 **나와 상대 사이의**
엣지만 지우고, 제3자의 팔로워 목록에서 차단 상대를 만나는 경우는 덮지 못한다.

### 조회를 전체 공개로 열었다

`blocks` 는 본인 행만 보이는데 `follows` 는 `using (true)` 다. 남의 프로필에서도
팔로워 수와 목록이 보여야 하기 때문이다. 본인 행만 열면 수 · 목록 · 맞팔 판정이
전부 `security definer` 함수를 타야 하고, 그 함수가 결국 같은 것을 공개하게 된다.
팔로우 그래프가 공개라는 것을 결정으로 적어 두는 편이 낫다.

### 팔로잉 피드는 뷰를 하나 더 두는 쪽으로

PostgREST 로 "내가 팔로우한 사람의 글"을 거르려면 계산 컬럼이나 필터 흉내가
필요하다. `posts_with_author` 를 `follows` 로 좁힌 뷰를 하나 두면 커서 · 컬럼 ·
정렬이 그대로라 **앱은 읽는 대상만 바꾼다**(`FeedSource`). 감싸는 뷰라 삭제 ·
차단 필터도 다시 쓰지 않는다.

탭 둘이 `FeedCubit` 하나를 공유한다. 탭마다 cubit 을 두면 작성 · 수정 · 삭제 ·
차단의 결과를 어느 목록에 반영할지 화면이 매번 정해야 한다. 대가는 탭을 옮길 때
다시 읽는 것(스크롤 위치 초기화)이고, 화면 주석에 적었다.

### 관계는 프로필 조회에 얹었다

`FollowActionCubit` 은 관계를 스스로 묻지 않고 화면이 `seed()` 로 심어 준다.
`profile_details` 가 프로필과 함께 내려주기 때문이다. `BlockActionCubit` 이
상태를 따로 조회하는 것과 갈리는데, 이유는 차단이 프로필 응답에 들어 있지
않아서다 — 차단 사실을 공개 뷰에 실을 수 없다.

낙관적 업데이트는 관계와 팔로워 수를 **한 상태에 함께** 담는다. 버튼만 바뀌고
수가 그대로면 실패한 것처럼 보이고, 되돌릴 값이 두 곳에 흩어지면 복원이
어긋난다.

### 차단 거부 문구는 방향 중립이다

`follows_insert_own` 의 차단 검사는 `is_blocked_with()` 라 양방향이다. 거부를
보는 쪽이 차단을 건 쪽이라고 가정할 수 없으므로 "지금은 팔로우할 수 없습니다"
하나로 끝낸다. 차단 계획의 [일반화된 규칙](../safety/plan-block.md)을 그대로
따랐다. 프로필 화면은 내가 차단한 상대에게는 아예 버튼을 그리지 않는다.

### 42501 을 데이터 원본에서만 코드로 바꾼다

공용 `SupabaseErrorMapper` 는 `42501` 을 일반 권한 오류로 옮긴다. 팔로우 삽입에서
오는 `42501` 은 사실상 차단 검사 하나뿐이라(`follower_id` 는 애초에 보내지 않는다)
`SupabaseFollowDataSource.followUser` 에서만 `FailureCode.followBlocked` 를 붙였다.
공용 mapper 에 넣으면 모든 RLS 거부가 팔로우 문구로 바뀐다.

## 범위

종목과 시점을 가린 과거 일봉 차트를 한 봉씩 넘기며 사고팔고, 판이 끝나면 채점해서
결과를 보여준다. 결과는 게시물로 피드에 올릴 수 있다.

이 기능이 [기획서 v0.4](../../overview.md)에서 이 앱의 주인공이 됐다. 다만 **소셜
쪽을 대체하지 않는다** — F1~F9는 그대로 두고, 판 결과를 나누는 자리로 쓴다.

## 확정한 결정과 근거

| 항목 | 결정 | 근거 |
|---|---|---|
| 시장 | **코인만.** Binance USDT 페어 20종목, 일봉 | 24시간 장이라 **휴장일 · 액면분할 · 배당 보정이 없다.** 주식으로 시작하면 시뮬레이터 로직보다 보정 로직을 먼저 만들게 된다. 공개 API가 키 없이 상장 이후 전 구간을 준다 |
| 시세 조달 | **받아서 seed 로 적재.** 런타임에 거래소를 부르지 않는다 | 같은 종목·같은 시작점이면 언제 돌려도 같은 봉이 나와야 채점을 신뢰할 수 있다. 오프라인으로 돌아가고 레이트 리밋도 없다 ([기획 §4.7](../../overview.md)) |
| 상태 보관 | **서버(Supabase).** 로컬 DB에 두지 않는다 | 기기를 바꿔도 기록이 남고, 공유한 결과 카드를 서버 데이터로 검증할 수 있다. 무엇보다 **심볼을 서버에만 둬야 숨김이 성립한다** |
| 종목·시작점 | **앱이 무작위로 고른다.** 사용자가 지정할 수 없다 | 고를 수 있으면 아는 구간을 고르게 되고, 그때 점수는 판단력이 아니라 암기력을 잰다 |
| 가격 표시 | **시작점을 100으로 정규화.** 원가격을 내려보내지 않는다 | `4261.48` 이 보이면 2017년 BTC 임을 바로 안다. 정규화는 종목·시점을 동시에 가리는 가장 싼 방법이다 |
| 숨김 강제 | **`market_candles` 에 클라이언트 GRANT 를 주지 않는다** | 화면에서 가리는 것은 우회된다. `security definer` RPC 만 읽게 하면 **심볼을 내려보낼 경로 자체가 없다** ([스키마 §16](../../schema.md)) |
| 공개 시점 | **판이 끝난 뒤에만** 종목·기간을 공개한다 | 판이 끝나면 숨길 이유가 사라지고, "무엇이었는지" 를 알아야 배우는 것이 남는다 |
| 한 판 길이 | 워밍업 60봉(보기만) + 진행 60봉(매매 가능) | 워밍업이 없으면 첫 봉에서 아무 근거 없이 사야 한다. 진행 60봉은 일봉 기준 약 2개월로, 한 판이 몇 분 안에 끝나 피드백이 빠르다 |
| 초기 자금 | 10,000 (단위 없음) | 가격이 100 으로 정규화되므로 통화 단위를 붙이면 오히려 혼란스럽다 |
| 주문 | **시장가만 · 현재 봉 종가 체결 · 롱만 · 수수료 0.1%** | 지정가·공매도·레버리지는 체결 모델을 먼저 만들어야 한다. 일봉 리플레이에서 봉 중간 체결은 추정이므로 종가로 고정한다 |
| 진행 | **"다음 날" 버튼으로 수동 진행** | 자동 재생은 속도 조절·일시정지가 따라온다. 수동이면 상태가 "몇 번째 봉인가" 하나다 |
| 결과 지표 | 수익률 · **buy&hold 대비** · 최대낙폭 · 매매 횟수 | 수익률만 보면 상승장에서 아무나 잘한 것처럼 보인다. buy&hold 대비가 "매매가 도움이 됐는가" 를 답한다 |
| 결과 공유 | **`posts` 에 첨부 유형이 하나 느는 형태** | 별도 게시물 테이블을 만들면 피드 · 반응 · 댓글 · 신고 · 차단을 전부 다시 만들어야 한다 |
| 소셜 참조 방향 | trade → post 의 `domain` 만. 반대는 결과 카드 위젯 하나로 제한 | 이 경계를 지켜야 시뮬레이터를 소셜과 무관하게 테스트할 수 있다 ([아키텍처 규칙 ⑥](../../architecture.md)) |

## 데이터 · 권한

### `market_candles` (5.1, 완료)

Binance 일봉 원시 시세다. 모양과 제약, **GRANT 를 주지 않는 이유**는
[스키마 §16](../../schema.md)이 단일 기준이다. 여기서는 앱 쪽 의미만 적는다.

- 사용자 데이터와 FK 관계가 없다. 판이 이 테이블을 **읽기만** 한다
- 앱은 이 테이블을 직접 조회하지 않는다 — 조회하려 하면 `42501` 로 막힌다.
  이것이 의도이며, `supabase/tests/market_candles_grant_check.py` 가 그 경계를 지킨다
- 데이터를 바꾸려면 `supabase/scripts/fetch_candles.py` 를 다시 돌린다
  ([개발환경 §5](../../setup.md))

## 단계

[기획 §8](../../overview.md)의 5단계를 그대로 따른다. 각 단계 끝에서 손에 남는 것이
있어야 한다.

| 단계 | 범위 | 끝났을 때 |
|---|---|---|
| **5.1** | 수집 스크립트 · `market_candles` · seed 적재 | `supabase db reset` 하나로 20종목 시세가 올라온다 — **완료** |
| **5.2** | 판 · 주문 테이블 · 판 시작/채점 RPC · RLS | 심볼을 숨긴 채 판을 만들고 채점하는 것이 DB 에서 검증된다 |
| **5.3** | 시뮬레이터 화면 (차트 · 다음 봉 · 매매 · 결과) | **혼자서 판을 끝까지 돌릴 수 있다** |
| **5.4** | 결과 카드 게시물 · 피드 표시 | 판 결과를 피드에 올리고 반응·댓글이 붙는다 |

**5.3 까지만 해도 제품으로 성립한다.** 공유(5.4)를 먼저 만들지 않는다 — 공유할 결과가
없는 공유 화면은 검증할 수 없다.

## 아직 정하지 않은 것

- **판 · 주문 테이블의 모양** — 컬럼, 소유자, 진행 상태를 어디에 두는가
- **판을 시작하고 채점하는 RPC 의 시그니처** — 무엇을 인자로 받고 무엇을 돌려주는가.
  특히 진행 중 남은 봉을 한 번에 내려줄지 봉마다 받을지 (한 번에 주면 클라이언트가
  미래를 볼 수 있다)
- **손익 계산의 위치** — 앱(Dart 순수 함수) 인가 DB 인가. 앱이면 테스트가 쉽고,
  DB 면 결과를 위조할 수 없다
- **화면 구성과 상태 모델** — 차트 · 잔고 · 주문 · 결과를 몇 개의 화면과 cubit 으로
  나누는가
- **차트 렌더링 방법** — 캔들 차트를 패키지로 그릴지 `CustomPainter` 로 직접 그릴지
- **판 중단 · 재개** — 앱을 껐다 켜면 진행 중인 판을 이어서 할 수 있는가
- **결과 카드의 저장 형태** — 게시물에 세션 id 만 걸지, 채점 결과 스냅샷을 함께 박을지
  (판 데이터가 바뀌면 과거 게시물이 달라지는 문제)

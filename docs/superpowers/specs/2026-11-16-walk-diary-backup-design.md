# 걷기(Life Log) 일기 백업 · 복원 설계

> 2026-11-16 · 상태: **기획(승인 대기)** · 앱: `apps/walk` · [걷기 허브](../../../apps/walk/docs/README.md)

## 1. 왜

일기 사진 · 동영상은 고를 때 앱 저장소로 사본을 만든다(긴 변 1600px JPEG 85, EXIF 제거, 동영상 720p · 30초 이하).
그래서 갤러리 원본을 지워도 일기는 남는다. 하지만 **앱을 지우거나 앱 데이터를 지우면 일기와 사진이 함께 사라진다.**
안드로이드 자동 백업은 일기 DB 와 사진을 담고 있지만 구글 클라우드 백업은 앱당 25MB 한도라, 사진이 쌓이면
한도를 넘어 **앱 전체 백업이 통째로 실패**한다. 사용자가 직접 들고 있을 수 있는 백업 파일이 필요하다.

사용자 걱정(원문 요지): 일기에는 개인정보가 많은데, 파일로 내보냈다가 유출되면 문제가 되지 않을까.

### 목표

- 설정에서 일기 전체를 **zip 파일 하나**로 기기의 원하는 위치에 저장한다.
- 그 파일을 골라 **복원**하면 다른 기기 · 재설치 뒤에도 일기 · 사진 · 동영상이 그대로 돌아온다.
- 유출 걱정을 덜도록 **비밀번호 암호화**를 고를 수 있다(기본 켬).
- 복원이 실패하거나 잘못 복원해도 **원래 데이터가 남는다**.

### 하지 않는 것(비목표)

- 구글 드라이브 API 직접 연동 · 계정 로그인 — 계정 연동을 늘리지 않는다. 드라이브에 두고 싶으면 저장 위치 창에서
  드라이브를 고르면 된다.
- 주기적 자동 백업(WorkManager) — 1차는 수동만(사용자 결정). 써 보고 다시 정한다. 대신 "마지막 백업" 시각을 보여준다.
- 기존 일기와 **합치기** — 1차는 바꿔 넣기만(§6).
- 물어보기 대화 · 알람 · 걸음 · 지도 위치 기록 백업 — 이 기능은 **일기** 백업이다.

### 실패로 치는 것(반목표)

- 백업에 API 키가 들어간다.
- 비밀번호를 잊으면 복원이 안 된다는 사실을 모른 채 암호화한다.
- 복원 도중 앱이 죽거나 파일이 깨져서 **원래 일기까지 잃는다**.
- 오래된 버전 앱이 새 포맷 백업을 반쯤 읽어 데이터가 어긋난다.

## 2. 저장 위치 — 결정: 위치 고르기(SAF) 로컬 zip

| 안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **SAF "저장 위치 고르기"(ACTION_CREATE_DOCUMENT)** | 로그인 없음. 기기 폴더 · 다운로드 · 구글 드라이브 앱 · USB 어디든. 복원도 같은 문서 고르기 창 | 매번 위치를 고른다 | **채택**(사용자 선택: 로컬 zip) |
| 공유 시트(share_plus) | 간편 | 메신저 용량 제한 · 재압축. 앱 캐시에 큰 파일이 남는다 | 뺌 |
| WorkManager 주기 백업 | 잊어도 된다 | 폴더 권한 유지 · 실패 알림 · 보관 개수 관리 | 다음 단계 후보 |
| Google Drive API | 진짜 클라우드 | OAuth · 앱 등록 · 계정 연동 | 뺌 |

구현 메모: `file_picker` 의 `saveFile` 은 안드로이드에서 **바이트 배열 전체를 메모리로** 받는다. 동영상이 쌓이면
수백 MB 가 될 수 있어 쓰지 않는다. 앱 캐시에 백업 파일을 먼저 만든 뒤, 작은 네이티브 채널
(`com.karma.walk/backup_file`)이 `ACTION_CREATE_DOCUMENT` 로 받은 URI 에 **스트림으로 복사**한다.
복원은 `ACTION_OPEN_DOCUMENT` 로 받은 URI 를 같은 채널이 캐시로 스트림 복사한다(기존 `file_picker` 의
`pickFiles` 도 캐시 사본을 만들므로 써도 된다 — 빌더 판단). 캐시 사본은 끝나면 반드시 지운다.

## 3. 범위

| 넣음 | 이유 |
|---|---|
| 스토리 · 기록(휴지통 포함) · 장소 · 태그 · 기록-태그 | 일기 그 자체. 휴지통도 넣어야 복원 뒤 휴지통 기한이 그대로 돈다 |
| 미디어 사본(`diary/media/` 의 본 파일 · 썸네일) | 일기의 사진 · 동영상 |
| 일기 설정(휴지통 보관 기간 · 자동 초안 문체 · 사진 포함) | 작고, 복원 뒤 같은 동작을 위해 |

| 뺌 | 이유 |
|---|---|
| 물어보기 API 키(보안 저장소) | 비밀 값. 백업 파일이 새면 요금이 새어 나간다. 키스토어에 묶여 있어 옮겨도 못 읽는다 |
| 위치 기록(`location.sqlite` · inbox) | 지도 설계에서 "이 폰에만 남긴다"로 정했다. 하루 이동 경로는 일기보다 민감하다 |
| 일기 잠금(PIN 해시 · 패턴 · 다시 잠김 시간) | 기기마다 다시 정하는 게 맞다. 잊은 PIN 이 따라오면 잠겨 버린다 |
| 물어보기 대화 · 위키 · 작업 폴더 · 알람 · 걸음 | 이 기능 범위 밖(일기 백업) |
| `diary/tmp/`(저장 전 사본) | 아직 일기가 아니다 |

기록 자체의 위치(기록에 붙인 장소 이름 · 위도 · 경도)는 **일기 내용이므로 넣는다** — 위치 기록(상시 추적)과 다르다.
설정 화면 안내 문구에 "API 키 · 위치 기록 · 잠금은 담지 않습니다"를 적는다.

## 4. 포맷과 버전

zip 한 파일. 파일 이름 `lifelog-diary-YYYYMMDD-HHmm.zip`, 암호화하면 `….lifelog`(§5).

```
manifest.json
diary.json
prefs.json
media/<id>.jpg
media/<id>.mp4
media/<id>_thumb.jpg
```

`manifest.json`:

```json
{
  "format": "lifelog.diary-backup",
  "formatVersion": 1,
  "diarySchemaVersion": 1,
  "appVersion": "1.0.0+1",
  "createdAt": "2026-11-16T21:30:00+09:00",
  "counts": {"stories": 3, "entries": 120, "places": 9, "tags": 14, "media": 210},
  "files": [{"path": "media/abc.jpg", "bytes": 312345, "sha256": "…"}],
  "dataSha256": "…"
}
```

- `diary.json` 은 테이블별 행 배열이다(`stories` · `places` · `tags` · `entries` · `media` · `entryTags`).
  컬럼 이름 · 값은 drift 행 그대로(날짜는 ISO-8601 문자열, `storeDateTimeAsText` 와 같다). **SQLite 파일을 통째로
  복사하지 않는다** — 스키마가 바뀌어도 JSON 을 읽어 그 시점 스키마로 넣을 수 있게.
- 미디어의 `path` · `thumbPath` 는 지금처럼 루트 기준 상대 경로(`media/…`)라 그대로 쓴다.
- 미디어 파일은 이미 압축돼 있어 zip 에 **저장(store)** 으로 넣고 JSON 만 deflate 한다.
- 읽을 때: `format` 이 다르면 "Life Log 일기 백업이 아닙니다". `formatVersion` · `diarySchemaVersion` 이 이 앱이
  아는 것보다 **크면** "앱을 업데이트한 뒤 복원하세요"로 거절한다. 작으면 단계별 변환 함수
  (`v1→v2` …)로 올린 뒤 넣는다. 지금은 v1 하나뿐이다.
- 모든 미디어 파일의 sha256 · 크기와 `diary.json` 의 sha256 을 맞춰 본 뒤에만 복원한다.

## 5. 암호화 — 결정: 선택, 기본 켬

일기 잠금(PIN)은 **앱 화면만** 막는다. DB · 사진 파일은 암호화돼 있지 않고, 백업 zip 도 그대로면 누구나 열어
일기 · 사진을 본다. 사용자가 유출을 걱정했으므로 내보내기 시트에서 **"비밀번호로 잠그기"를 기본으로 켜 둔다.**
끄면 "이 파일은 누구나 열 수 있어요. 컴퓨터에서 사진을 꺼낼 때만 끄세요"를 보여준다.

- 켜면: 위 zip 을 통째로 감싼다. 컨테이너(빌더가 `domain` 밖 `data/diary/backup/` 에 둔다):
  - 헤더: 매직 `LLBK` · 컨테이너 버전 1 · KDF 이름 · 반복 수 · salt(16B) · 기본 nonce(12B · 앞 8B 무작위)
  - 키: PBKDF2-HMAC-SHA256, 600,000회(OWASP 2023 권고), 32B 키
  - 본문: AES-256-GCM, **1 MiB 덩어리** 별로 암호화(nonce = 기본 nonce 앞 8B ‖ 덩어리 번호 4B, AAD = 헤더 ‖
    덩어리 번호 ‖ 마지막 여부). 큰 파일도 메모리에 다 올리지 않고, 덩어리 순서 바꾸기 · 잘라내기를 잡는다
  - 틀린 비밀번호 · 손상은 첫 덩어리 태그 검증에서 걸린다 → "비밀번호가 틀렸거나 파일이 손상됐어요"
- 비밀번호: 8자 이상, 두 번 입력. **잊으면 복원할 수 없다**는 문구를 확인란과 함께 보여준다. 비밀번호는 저장하지 않는다.
- 라이브러리는 빌더 판단(`cryptography` + `cryptography_flutter`, 또는 Kotlin `javax.crypto` 를 채널로). 기준:
  600,000회 PBKDF2 가 중급 폰에서 2초 안쪽, 1 MiB 덩어리 스트리밍. Java GCM 은 복호화 때 전체를 버퍼링하므로
  덩어리마다 새 Cipher 를 쓴다.
- 복원 시 파일 첫 4바이트로 판별한다: `PK\x03\x04` 면 일반 zip, `LLBK` 면 비밀번호를 묻는다.

## 6. 복원 — 결정: 바꿔 넣기 + 되돌리기 한 번

**합치기 대신 바꿔 넣기**를 고른 이유: 쓰임새가 "재설치 · 새 폰"이라 현재 일기가 거의 비어 있다. 합치기는
같은 이름 다른 id 의 장소 · 태그, 기본 스토리(`Story.dailyId`), 지운 기록 되살아남 같은 충돌 규칙이 많고, 결과를
예측하기 어렵다. 바꿔 넣기는 같은 id 충돌이 생기지 않는다. 대신 아래 안전장치로 "잘못 복원"을 막는다.

흐름:

1. 설정 → 일기 → 백업 → "백업에서 복원" → 파일 고르기 → (암호화면) 비밀번호
2. **검증 단계**(현재 데이터에 손대지 않음): 캐시의 작업 폴더에 풀고 manifest · 버전 · sha256 · JSON 파싱 ·
   참조 무결성(기록의 스토리 · 장소, 미디어의 기록)을 확인한다. 실패하면 여기서 끝, 작업 폴더를 지운다.
3. 확인 다이얼로그(`AppConfirmDialog`, 파괴적): "백업 날짜 · 기록 N개 · 사진 · 영상 M개로 **지금 일기를 바꿉니다**.
   지금 일기는 되돌리기용으로 잠시 보관됩니다."
4. **되돌리기 지점 만들기**: 현재 일기를 같은 포맷(암호화 없이)으로 앱 내부 `diary_restore_undo/` 에 내보낸다.
   한 개만 둔다(새로 복원하면 덮어씀). 자동 백업 규칙에서 뺀다(§7).
5. **바꾸기**:
   - 미디어: 현재 `diary/media/` 를 `diary/media.old/` 로 이름 바꾸고, 작업 폴더의 `media/` 를 `diary/media/` 로 옮긴다
     (같은 파일 시스템이면 rename. 캐시와 문서 폴더가 다를 수 있으니 작업 폴더는 `diary/` 아래 `restore_staging/` 에 둔다).
   - DB: 한 트랜잭션에서 일기 테이블을 비우고 JSON 행을 넣는다. 기본 스토리가 백업에 없으면 `_ensureDailyStory` 와
     같은 규칙으로 만든다. 일기 설정을 적용한다.
   - 트랜잭션이 실패하면 `media.old/` 를 되돌려 놓는다(DB 는 롤백됨).
   - 성공하면 `media.old/` 를 지운다.
6. 앱 시작 시 `media.old/` 나 `restore_staging/` 가 남아 있으면(도중에 죽음) 정리한다: DB 의 미디어 경로가 가리키는
   파일이 `media/` 에 다 있으면 `media.old/` 를 지우고, 아니면 `media.old/` 를 되돌린다. 고아 청소(`cleanOrphans`)는
   이 둘을 건드리지 않는다.
7. 설정에 "복원 전으로 되돌리기"(되돌리기 지점이 있을 때만) 행. 누르면 4의 파일로 같은 복원 흐름을 돈다(확인 다이얼로그 포함).

- 일기가 잠겨 있으면(`LockUnlocked` 아님) 내보내기 · 복원 행을 막는다 — 잠금을 우회해 일기를 빼낼 수 없게.
- 복원 중에는 전체 화면 진행 표시로 다른 조작을 막는다. 일기 화면들은 drift 스트림을 보고 있어 복원 뒤 저절로 갱신된다.
- 복원 뒤 휴지통 정리 · 고아 청소는 평소처럼 돈다.

## 7. 안드로이드 자동 백업 규칙

지금은 일기 DB 와 미디어가 클라우드 백업 · 기기 이전 모두에 들어간다. 사진이 25MB 를 넘으면 클라우드 백업이
**앱 전체로 실패**해, 오히려 작은 데이터(알람 · 설정 · 일기 글)까지 백업되지 않는다.

결정:

- `backup_rules.xml`(API ≤30, 클라우드)과 `data_extraction_rules.xml` 의 `<cloud-backup>` 에서
  `app_flutter/diary/` 를 뺀다(미디어 · tmp · 복원 작업 폴더). **일기 DB(`diary.sqlite`)는 남긴다** — 글은 작다.
  복원된 기록의 사진은 없을 수 있고, 이미 있는 "사진 없음" 표시(`entry_media_view.dart` 의 `_Missing`)가 보인다.
- `<device-transfer>`(케이블 · 기기 간 이전, 25MB 한도 없음)에는 미디어를 그대로 둔다.
- 되돌리기 지점(`diary_restore_undo/`)은 둘 다에서 뺀다.
- 설정 안내 문구를 "사진 · 동영상은 구글 자동 백업에 들어가지 않아요. 백업 파일을 만들어 두세요"로 바꾼다.
- 경로는 구현 때 `getApplicationDocumentsDirectory()` 가 `app_flutter` 임을 에뮬레이터에서 확인한다.

## 8. 화면

설정 → 일기 화면에 "백업" 섹션(새 위젯 `diary_backup_section.dart`, 기존 섹션 파일은 건드리지 않음):

```
백업
  [↑] 백업 파일 만들기          마지막 백업: 3일 전
  [↓] 백업에서 복원
  [↺] 복원 전으로 되돌리기       (되돌리기 지점이 있을 때만)
  API 키 · 위치 기록 · 잠금은 담지 않습니다.
```

내보내기 시트: 비밀번호로 잠그기 스위치(기본 켬) · 비밀번호 두 칸 · "잊으면 복원 불가" 확인 · [저장 위치 고르기].
진행 중: 단계(모으는 중 · 암호화 중 · 저장 중)와 퍼센트. 완료: `AppSnackBar` "백업했어요 (사진 · 영상 M개, 123MB)".
마지막 백업 시각은 성공했을 때만 SharedPreferences 에 적는다. 30일이 넘으면 행에 "오래됨" 표시(알림은 없음).

공통 위젯(`AppListTile` · `AppConfirmDialog` · `AppButton` · `AppSnackBar`)과 토큰만 쓴다. l10n arb 는 필요한 키만 더한다.

  공간 부족 · 취소) · `DiaryBackupRepository` 인터페이스 · 유스케이스(`exportDiary` · `inspectBackup` · `restoreDiary` ·
  `undoRestore`).
- `data/diary/backup/`: JSON 직렬화(drift 행 ↔ map) · zip 쓰기/읽기(`archive` 패키지, 파일 스트림) ·
  암호 컨테이너 · 복원 트랜잭션 · 시작 시 정리. 네이티브 채널 래퍼.
- `presentation/settings/`: `DiaryBackupCubit`(+ freezed union 상태) · 섹션 · 시트.
- 무거운 일(압축 · 해시 · 암호화)은 `Isolate.run` 으로 UI 스레드 밖에서.
- 저장 공간: 내보내기 전 캐시 여유 공간이 예상 크기(미디어 합 + 여유)보다 작으면 실패로 알린다. 복원은 백업 크기의 2배.

## 10. 테스트(완료 조건)

- 왕복: 스토리 · 기록(휴지통 포함) · 장소 · 태그 · 사진 · 동영상+썸네일을 넣은 메모리 DB + 임시 폴더 → 내보내기 →
  비우기 → 복원 → 모든 행 · 파일 바이트 같음. 암호화 켬/끔 둘 다.
- 틀린 비밀번호 · 덩어리 하나 바꾼 파일 · 잘린 파일 · sha256 안 맞는 미디어 · 모르는 `format` · 더 큰 `formatVersion` →
  각각의 실패, **현재 데이터 그대로**.
- 트랜잭션 도중 실패(가짜 저장소) → DB · `media/` 원상복구. 시작 시 정리의 두 갈래.
- 되돌리기: 복원 → 되돌리기 → 복원 전 데이터와 같음.
- 백업에 API 키 · 위치 · 잠금 값이 없음(파일 목록과 JSON 키 검사).
- cubit 상태 전이 · 잠김 상태에서 행 막힘 · 섹션 위젯 테스트.
- 에뮬레이터: 내보내기(다운로드 폴더) → 앱 데이터 지우기 → 복원 → 피드에 사진 보임.
